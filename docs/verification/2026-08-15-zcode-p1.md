## Probe method

The Electron app was not driven directly. Sessions were driven two ways:

1. Headless one-shots: `node zcode.cjs --prompt ... [--mode plan]`.
2. Interactive protocol: `node zcode.cjs app-server` speaking the "ZCode
   Protocol" (line-delimited JSON, JSON-RPC-like but with no `jsonrpc` key)
   from a custom stdio driver: `session/create` (needs
   `workspace.workspaceKey` + `workspacePath`), `session/subscribe`
   (`deliveryKind: "desktop-continuous"`), `session/send` (`content`),
   `session/stop`, answering server→client `interaction/requestPermission`
   and `session/requestRuntimePreferences` requests. This is the same
   protocol surface the desktop app uses, so permission/interrupt flows are
   representative of interactive use.

Registry state was observed via `stream-deck-agents sessions list` polled at
250ms–1s. The physical tile face (ZC chip pixels) is not automatable; chip
rendering is covered by the P0 plugin unit tests, and the deployed 0.3.0.0
plugin process was confirmed live.

## Probe results (all OBSERVED)

1. **Session start → tile row.** First headless prompt created registry row
   `sess_f2e9ed68...`, provider `zcode`, within ~1s of process start.
   Via app-server, `session/create` alone does not fire `SessionStart`; the
   row appears when the first prompt is sent (hooks materialize lazily).
2. **Prompt → working; turn end → idle.** Observed repeatedly, e.g.
   01:52:17.9Z SessionStart→idle, 01:52:18.0Z UserPromptSubmit→working,
   idle again at turn end (Stop). A two-tool 16s turn stayed `working`
   throughout and dropped to `idle` within ~1s of the final message.
3. **Permission → waiting → answered → working/idle.** In app-server build
   mode, `touch marker3.txt` raised `interaction/requestPermission`
   (riskLevel high): row `waiting` at 01:59:50Z; held 6s; answered
   `{"decision":"allow"}`; row back to `working` at 01:59:56Z, `idle` at
   02:00:01Z, and the file was really created. Full waiting→working→idle
   cycle confirmed.
4. **Interrupt.** Two variants probed, both via `session/stop` (the desktop
   stop control's protocol path):
   - *Mid-tool:* stop issued during a `sleep 20` tool call. Accepted, turn
     ended, no PostToolUseFailure (or any further hook event) delivered;
     row stayed `working` until the lease pruned it.
   - *Between tool calls:* a two-command turn (`echo`, then a separate
     `sleep 3`), with the stop fired the instant the first tool's output
     event arrived. The event stream pins the placement: PostToolUse of
     tool 1 delivered at epoch-ms ...698368, stop sent ...698369 and
     accepted ...698381, `turn.completed` ...698384, and no second
     PreToolUse ever appeared — the interrupt landed after tool 1 completed
     and before tool 2 began. Zero `PostToolUseFailure` events in the
     entire stream; the row stayed `working` through a 15s post-stop hold
     and after (`sess_ff86872f`, last update 02:18:18.364Z = the tool-1
     PostToolUse).
   In both variants the docs' hedge is the observed 0.16.3 behavior: an
   interrupt delivers no failure event and the tile stays `working` until
   the next event or the lease. No probe in this run managed to elicit a
   `PostToolUseFailure` event at all (the `is_interrupt` mapping in the
   decoder remains covered only by unit tests). Accepted for v1; recorded
   as a known gap.
5. **Title latency.** `first_input` titles appeared in the registry within
   one poll (~1–2s) of session start. The auto-generated rewrite was then
   measured directly (`sess_22260d2b`, 250ms polls against both stores):
   zcode wrote `title_source = 'generated'` ("Why the sky is blue") with
   its own `time_title_updated` = 1786846760437 (02:19:20.437Z); the DB
   poll observed it 100ms later; the registry row carried it at
   02:19:21.929Z — **1.39s after the DB observation (~1.49s after zcode's
   write), within the 2s title cadence.** WAL evidence captured at the
   rewrite moment: `db.sqlite-wal` held 4,132,392 bytes while `db.sqlite`
   itself was unchanged (size 1,822,720 bytes, mtime 17 minutes older than
   the write) — the generated title existed only in the WAL when the
   per-pass resolver picked it up, so the live WAL read path is
   substantiated, not assumed.
6. **Ghost probe.** This build has no `/side` or `/btw` commands (checked
   `--help` slash list). Closest analogs probed:
   - Subagent: a prompt forcing the Agent (Task) tool ran a real
     `subagent_child` session (`sess_subagent_agent_fb26747c...`, confirmed
     in zcode's DB with parent Agent tool `completed`). **No hook events
     fired for the child; no extra registry row appeared.**
   - Headless one-shots: each `--prompt` run creates a real session and
     therefore a real row that ends `idle` and lingers until the lease.
   - Scheduled runs (`automation/*` protocol methods exist): not probed —
     creating persistent automations on the live machine was out of scope
     for this pass; noted as the one unprobed ghost source.
   **Decision: ACCEPT.** No payload filtering (`source`/`agent_type`/`cwd`)
   is needed: subagents emit no hooks, and one-shot rows are real sessions
   correctly covered by the 1h lease. No follow-up fix task.
7. **Lease prune.** Method: simulated (waiting an hour was not). All 9
   zcode rows' `updated_at` backdated 2h by direct SQL against
   `registry.sqlite3`, then the daemon's next periodic prune pass
   (60s cadence) removed all 9 zcode rows in one pass; the 8 claude/codex/
   kimi rows survived (24h TTL). Observed via `sessions list` at 5s polls;
   rows gone within ~75s of the backdate.

## Divergences and follow-ups

1. **Docs gap — CLI model config.** `~/.zcode/cli/config.json` needs
   `model` + `provider` blocks for any CLI/headless use (details above);
   hooks alone are fine for the desktop app. Follow-up: add a note to
   docs/hook-configuration.md §ZCode.
2. **Headless plan-mode deny strands `waiting`.** Twice observed: under
   `--prompt --mode plan`, a denied tool ends the run with a final message
   but the row stays `waiting` forever (PermissionRequest was the last
   event delivered; no Stop landed after it — either the exiting process
   drops the Stop dispatch or it raced ahead of the PermissionRequest hook
   process). Interactive (app-server) deny and allow flows both reach
   `idle` correctly. Accepted: the 1h lease clears such rows. Follow-up
   candidate only if headless zcode becomes a real workflow.
3. **Interrupt gap confirmed** (probe 4): no failure event on interrupt in
   0.16.3, both mid-tool and between tool calls; tile stays `working`
   until the next event or the lease. Already documented as accepted v1
   behavior; now recorded as observed.
4. **Not automatable in this pass:** physical tile pixels (ZC chip), the
   Electron app's own UI actions (no TUI package; app not scriptable), and
   `automation/*` scheduled runs. Each is noted where relevant above.
