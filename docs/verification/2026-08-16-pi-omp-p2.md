## Mid-verification incident: concurrent-agent schema clobber

At 08:07:53Z — mid-way through the omp probes — a **different Paseo agent**
working on the `attention-inbox-grid` branch on this same machine ran its
own installer. That branch also names its schema v6 but with different
columns (`origin_kind`/unread instead of main's `model`), so its init saw
`user_version = 6` and accepted the database unmigrated; the daemon it
started then failed every projection query (`sessions list failed: no such
column: origin_kind`; 61 `maintenance_failed` log entries at the 2s
cadence). Helper events delivered during the ~2-minute window ran through
the mismatched executable and one omp Stop event was lost. This worktree's
build was reinstalled at ~08:09:50Z, after which `sessions list` and
maintenance recovered immediately and all 28 rows (incl. both omp rows)
were intact. The two branches' schema forks are **incompatible siblings
with the same version number** — whichever installs second breaks the
other. Flagged for the controller; not a P2 code defect, but the version
collision needs an adjudicated resolution before either branch merges.

## Divergences and follow-ups

1. **pi mid-tool abort delivery race** (probe 7): terminal StopFailure and
   the final PostToolUse spawn as independent detached processes ~3ms
   apart and can land out of order, leaving the tile working (2/5 trials).
   Docs now state the observed behavior (pi § Known gaps). Follow-up
   candidate: serialize the shim's helper spawns (chain on child exit) —
   a contained change to the shared spawn helper in both shims.
2. **pi abort-during-tool shows the error tile** (3/5 trials, and always at
   the event level): pi 0.84.2 reports an aborted tool as an errored turn
   (`stopReason: "error"`, not `"aborted"`). The docs' behavior section now
   says so. Not a defect — the shim maps what pi reports — but it means
   Escape's tile outcome differs by what was running when the user pressed
   it.
3. **omp task-tool spec approval doesn't reliably raise
   `tool_approval_requested`** (probe 2/4): the Change/Acceptance dialog
   left the row at working in 2 of 3 approvals; ordinary bash approval and
   one task approval showed waiting. omp-internal approval-path
   difference; observe-only handler unaffected; cosmetic tile impact.
   Docs qualified. Follow-up only if omp's approval events consolidate in
   a later build (fork-churn rule applies).
4. **omp `/new` strands the old row** (probe 6): no per-session end event
   exists mid-process, so the old row lingers at its last status until the
   24-hour lease (or a resume-and-quit) — the 1-hour lease is zcode-only
   (`ZCODE_STALE_SESSION_TTL_MS`); pi/omp use the 24h default. Docs now
   state this. Accepted: same lease-backstop reasoning as zcode's
   interrupt gap.
5. **Schema v6 fork collision** (incident above): needs controller/user
   adjudication across branches; nothing committed here can fix it
   unilaterally.
6. **Not automatable in this pass:** physical key-face pixels (PI/OM
   chips) — plugin unit tests plus the live plugin process are the
   accepted evidence, per the zcode P1 precedent waiver; and pi subagent
   rows (no such feature exists in 0.84.2 to probe).

## Race fix confirmation (fix round 1, same run date)

The mid-tool-abort delivery race (divergence 1) was fixed by serializing
helper spawns in both shims: a FIFO promise queue in `emit` — each spawn
link starts only after the previous helper's exit or error settles, every
link fail-soft so a dead helper never wedges the queue. Handlers stay
synchronous. Pinned by ordering tests in both harness suites (the fake
port's completions are test-controlled; the second payload is not spawned
until the first completes, and a rejected first link still lets later
payloads through in order).

**Live re-probe** (same method as probe 7: tmux-driven pi 0.84.2 TUI,
bash `sleep 20`, Escape ~2s after the tool's Elapsed counter appeared,
registry read via read-only SQLite after each trial): **6/6 trials ended
on the error tile; 0 stuck on working** (pre-fix: 3/5 error, 2/5 stuck).
A follow-up clean turn cleared the error to idle, and quitting removed the
row — the error-then-recover behavior the docs describe.

Environment note for this re-probe: between the fix and the re-probe the
live registry moved to schema v7 (the `attention-inbox-grid` branch
renumbered its origin/unread migration on top of main's v6, resolving the
version collision flagged above, and deployed). This branch's v6 build
fail-closes against v7, so the daemon/helper running during the re-probe
was the v7 binary restored from that branch's build artifact, with this
branch's fixed shims rendered onto it by hand using the installer's exact
logic (marker first line, token substituted, atomic 0600). The serialized
shims and the v7 helper interoperate — the shim/wire contract is
version-agnostic. This worktree's own installer remains blocked on v7
until main absorbs the v7 migration and this branch merges it.

Doc corrections in the same fix round: the pi/omp prune lease is the
**24-hour default** (`STALE_SESSION_TTL_MS`) — the 1-hour lease is
zcode-only (`ZCODE_STALE_SESSION_TTL_MS`); divergence 4 above and both
provider sections of docs/hook-configuration.md corrected. The pi
Known-gaps stuck-working bullet was replaced by the serialized-spawn
behavior note, and the shims' module docstrings and the AGENTS.md shim
bullet no longer describe spawns as unordered fire-and-forget.
